

Technical Specifications
Only Coffee Mobile App

1. INTRODUCTION

1.1 EXECUTIVE SUMMARY

1.1.1 Project Overview
Only Coffee represents a transformative mobile-first coffee ecosystem designed to revolutionize the coffee ordering and engagement experience. This comprehensive platform integrates mobile ordering, gifting, loyalty programs, and delivery services into a unified brand experience that bridges the gap between traditional coffee shop operations and modern digital consumer expectations.

1.1.2 Core Business Problem
The coffee industry faces significant challenges in meeting evolving consumer demands for convenience, personalization, and seamless digital experiences. The market for coffee apps has recently developed due to the rising trend of coffee culture and more customers' preference for convenience, with approximately 48% of consumers using mobile apps to order coffee regularly. Current solutions are fragmented across multiple platforms, creating friction in the customer journey and limiting opportunities for meaningful engagement and loyalty building.

1.2 SYSTEM OVERVIEW

1.2.1 Project Context
Business Context and Market Positioning

Starbucks reports that 31% of total transactions at U.S. company-operated stores are made via mobile app, while U.S. coffee chain sales grew by 8% year-over-year, reaching a market size of $49.5 billion. Only Coffee enters this expanding market with a differentiated approach that combines:
  Multi-platform Integration: Seamless connection with Toast POS, DoorDash, Uber Eats, and Grubhub
 Social Commerce: Native iMessage gifting and social sharing capabilities
 Comprehensive Service Model: From individual orders to large-scale catering solutions

Current System Limitations
Traditional coffee ordering systems suffer from:

 Fragmented customer experiences across multiple platforms  Limited personalization and loyalty integration
 Inefficient pickup scheduling leading to wait times and order quality issues
 Disconnected delivery and catering services
 Minimal social engagement and viral marketing capabilities

Integration with Existing Enterprise Landscape
The Toast platform REST web service APIs make it easier and more efficient to work with location data, providing comprehensive software as a service (SaaS) products and financial technology solutions for restaurants. Only Coffee leverages this established ecosystem while extending capabilities through:
Toast POS Integration: Real-time menu synchronization, order processing, and inventory management
Payment Processing: Stripe, Apple Pay, and Google Pay integration for secure transactions

 Delivery Networks: White-label integration with major delivery platforms
 Analytics Pipeline: Segment to Amplitude data flow for comprehensive insights

1.2.2 High-Level Description
Primary System Capabilities
Only Coffee delivers a comprehensive coffee ecosystem through:

1. Intelligent Store Discovery: Geolocation-based store, truck, and kiosk identification with real-time availability
2. Advanced Order Management: Custom drink builder with dynamic pricing and scheduled pickup slots
3. Integrated Loyalty System: Points-based rewards with automatic accrual and redemption
4. Social Gifting Platform: iMessage extension for seamless gift card and free coffee sharing
5. Multi-Channel Delivery: Unified interface for DoorDash, Uber Eats, and Grubhub services
6. Enterprise Catering: Large-order management with approval workflows and delivery coordination
7. Social Commerce Engine: Review and sharing system across multiple social platforms
Major System Components




Core Technical Approach
The system employs a microservices architecture built on:

 Cloud-Native Infrastructure: AWS ECS Fargate with auto-scaling capabilities
 Event-Driven Communication: SNS/SQS for reliable service coordination
  Real-Time Processing: Redis for slot management and caching
 API-First Design: RESTful services with comprehensive OpenAPI documentation
  Cross-Platform Mobile: Native iOS (Swift/SwiftUI) and Android (Kotlin/Compose) applications

3. TECHNOLOGY STACK

3.1 PROGRAMMING LANGUAGES

3.1.1 Backend Development
TypeScript 5.x serves as the primary backend language, leveraging NestJS 11.1.6 as the core framework. TypeScript provides robust type

safety features and is fully compatible with Node.js 20, with NestJS supporting Node.js version 12 and up. The selection criteria prioritize:
 Type Safety: Compile-time error detection and enhanced developer experience
 Enterprise Scalability: Proven performance in large-scale applications
 Framework Ecosystem: Extensive library support and community adoption
 Maintainability: Strong tooling support and code organization capabilities

3.1.2 Mobile Development
Swift 5.10 powers iOS development, released in March 2024 with improved concurrency model and full data isolation to prevent data races. SwiftUI provides declarative UI development with iOS 16+ compatibility, offering new features like navigation improvements and enhanced performance.
Kotlin drives Android development with Jetpack Compose supporting Android 5.0 and later (API level 21+). The Compose Compiler 1.5.15 targets Kotlin 1.9.25, ensuring compatibility with the latest language features.
Selection Justification:

Native Performance: Platform-optimized execution and system integration
Platform Features: Full access to iOS 16+ and Android 9+ capabilities
Developer Experience: Modern declarative UI frameworks (SwiftUI, Compose)
Long-term Support: Stable language evolution and platform commitment

3.1.3 Infrastructure and Tooling
JavaScript/TypeScript extends across the development pipeline for:

  Build automation and CI/CD scripting
 Infrastructure configuration and deployment tools  Development tooling and testing frameworks

3.2 FRAMEWORKS & LIBRARIES

3.2.1 Backend Framework Stack
NestJS 11.1.6 provides the core backend framework, built with TypeScript and combining Object Oriented Programming, Functional Programming, and Functional Reactive Programming paradigms. NestJS utilizes Express under the hood while providing compatibility with Fastify for enhanced performance options.
Core Dependencies:

 @nestjs/core: 11.1.6 - Framework core functionality
  @nestjs/common: 11.1.6 - Common utilities and decorators
  @nestjs/platform-express: 11.1.6 - Express platform integration
  @nestjs/swagger: Latest - OpenAPI documentation generation
  @nestjs/microservices: Latest - Event-driven architecture support

Justification: NestJS provides enterprise-grade architecture patterns, built- in dependency injection, comprehensive testing support, and seamless integration with TypeScript's type system.

3.2.2 Mobile Framework Stack
iOS Development Stack:

 SwiftUI: Native declarative UI framework with Swift 6 language mode support and main actor isolation
 Combine: Reactive programming framework for data flow management
 Foundation: Core system services and utilities
 UIKit: Legacy UI components and system integration

Android Development Stack:

 Jetpack Compose: Modern declarative UI toolkit with 7 Maven Group IDs providing targeted functionality subsets
 Compose Runtime: Used by production apps including Threads, Google Drive, and SoundCloud
 Kotlin Coroutines: Asynchronous programming and concurrency management
 Android Architecture Components: Lifecycle-aware components and data binding
Compatibility Requirements:

  iOS: Minimum iOS 16.0, targeting latest iOS versions
  Android: Minimum API level 28 (Android 9), targeting API level 34+

3.2.3 Cross-Platform Shared Components

5. SYSTEM ARCHITECTURE

5.1 HIGH-LEVEL ARCHITECTURE

5.1.1 System Overview
Only Coffee employs a microservices architecture where software is composed of small, independent services that communicate through well- defined APIs, with each service supporting a specific task or business goal. The system follows Command Query Responsibility Segregation (CQRS) pattern, separating the responsibilities for handling command input (writing data) from query input (reading data) to optimize each side of the application independently.
The architecture is built on event-driven principles where events trigger and communicate between decoupled services. Event-driven architectures have three key components: event producers, event routers, and event consumers, with producer services and consumer services being decoupled to allow independent scaling, updating, and deployment.
Core Architectural Principles:

Service Independence: Each service is easier to update or replace without affecting the rest of the system, with communication happening through APIs or message brokers rather than direct calls

 Event-Driven Communication: Event producers and event consumers are decoupled with all interactions between microservices being asynchronous
 API-First Design: RESTful services with comprehensive OpenAPI documentation enabling consistent integration patterns
 Cloud-Native Infrastructure: Automatic scaling leveraging Application Auto Scaling service to increase or decrease the desired number of tasks automatically
System Boundaries and Major Interfaces:

The system integrates with external services through standardized APIs and event-driven patterns. Toast POS integration handles menu synchronization and order processing, while delivery partners (DoorDash, Uber Eats, Grubhub) connect through unified adapter patterns. Payment processing flows through Stripe with Apple Pay and Google Pay integration, and social platforms connect via OAuth 2.0 for gifting and sharing capabilities.

5.3 TECHNICAL DECISIONS

5.3.1 Architecture Style Decisions and Tradeoffs
Microservices vs Monolithic Architecture:

The decision to adopt microservices architecture follows the concept of SOA (Service Oriented Architecture), where software is composed of small, independent services that communicate through well-defined APIs, with each service supporting a specific task or business goal. This choice provides several advantages:
 Independent Scaling: Each microservice can be independently scaled, maintained and updated without affecting the entire application, with teams able to choose different technologies for each service based on requirements, and fault isolation ensuring high availability
 Technology Flexibility: Different services can use optimal technology stacks for their specific requirements

async handleProcessingError( message: SQSMessage, error: Error
): Promise<void> {
const retryCount = this.getRetryCount(message);
const maxRetries = this.getMaxRetries(message.eventType);

if (retryCount < maxRetries) {
await this.scheduleRetry(message, retryCount + 1);
} else {
await this.sendToDeadLetterQueue(message, error);
await this.alertOperations(message, error);
}
}

private async scheduleRetry( message: SQSMessage, retryCount: number
): Promise<void> {
     const delay = Math.pow(2, retryCount) * 1000; // Exponential backoff

await this.sqsClient.sendMessage({ QueueUrl: message.queueUrl, MessageBody: message.Body,
DelaySeconds: Math.min(delay / 1000, 900) // Max 15 minutes
}).promise();
}
}

async handleCriticalAlert(alert: Alert): Promise<void> {
// 1. Immediate assessment
const healthStatus = await
this.healthCheckService.performFullCheck();

// 2. Auto-remediation attempts
if (alert.type === 'HIGH_ERROR_RATE') {
await this.attemptAutoRemediation(alert);
}

// 3. Notification and escalation
await this.notificationService.sendCriticalAlert({ alert,
healthStatus,
runbookUrl: this.getRunbookUrl(alert.type), escalationPolicy: 'critical-incidents'
});

// 4. Create incident record
await this.incidentService.createIncident({ severity: 'critical',
description: alert.description,
affectedServices: this.identifyAffectedServices(alert), responseTeam: this.getResponseTeam(alert.type)
});
}
}

9.2 GLOSSARY

Application Performance Monitoring (APM): Tools and practices for monitoring and managing the performance and availability of software applications, including response times, error rates, and resource utilization.
Blue-Green Deployment: A deployment strategy that reduces downtime and risk by running two identical production environments, switching traffic between them during updates.
Circuit Breaker Pattern: A design pattern that prevents cascading failures by monitoring for failures and temporarily blocking requests to failing services.
Container Orchestration: The automated deployment, management, scaling, and networking of containers across a cluster of machines.

Event-Driven Architecture (EDA): An architectural pattern where services communicate through the production and consumption of events, promoting loose coupling and scalability.
Infrastructure as Code (IaC): The practice of managing and provisioning computing infrastructure through machine-readable definition files rather than manual processes.
Microservices Architecture: An architectural approach that structures an application as a collection of small, independent services that communicate through well-defined APIs.
Multi-Factor Authentication (MFA): A security method that requires users to provide two or more verification factors to gain access to a resource, application, or system.
Point of Sale (POS) System: A combination of software and hardware that allows businesses to conduct sales transactions, manage inventory, and process payments.
Serverless Computing: A cloud computing execution model where the cloud provider dynamically manages the allocation and provisioning of servers.
Service Level Agreement (SLA): A commitment between a service provider and client that defines the level of service expected, including availability, performance, and responsibilities.
Time to Live (TTL): A mechanism that limits the lifespan of data in a computer or network, commonly used in caching systems to determine when cached data should expire.
